# Работа в репозитории

- Перед правкой проверь состояние рабочей копии и прочитай ближайшие реализации и проверки. Сохраняй имеющиеся изменения пользователя. Сверяй доступные команды с конфигурацией именно этого проекта.
- Держи изменение в границах задачи. Переиспользуй существующий тип или функцию, если совпадают их смысл и поведение. Новый модуль называй по назначению. При переносе обнови все места использования и удали ставший лишним код своей правки.
- Выбирай понятные английские имена для идентификаторов. Инструкции проекта пиши по-русски. В комментарии объясняй причину нетривиального решения, например почему повтор команды проверяется до версии партии. Для публичного контракта опиши единицы, допустимые значения и ошибки.
- При изменении запуска обнови README. При изменении границ приложения обнови ARCHITECTURE.md. Фактическое состояние реализации и планируемые возможности обозначай отдельно.
- Используй синтетические партии и отдельные временные базы. Сессионные ключи, содержимое пользовательских баз и локальные секреты исключай из примеров, журналов и коммитов. Перед коммитом проверь состав и diff изменений. Операции с удалённым репозиторием выполняй в рамках запроса пользователя.

## Объёмные задачи и документация

В ROADMAP.md оставляй приоритет, статус, ближайший результат и ссылку. Для крупной функции веди один документ в docs/features/ и добавляй его в [каталог функций](../../docs/features/README.md). Включай сценарий пользователя, правила, данные, ошибки и критерии приёмки. Различай доступные возможности и последующие шаги. Для технического решения с долгосрочными последствиями запиши причину и условие пересмотра в профильном документе. Ссылайся на реализацию и проверки и обновляй описание вместе с кодом. Для небольших исправлений достаточно актуализировать существующий документ.

## Один проверяемый шаг

1. При продолжении разработки сопоставь последний принятый шаг в [ROADMAP.md](../../ROADMAP.md) с веткой, локальными правками и фактическим поведением приложения.
2. До изменения сформулируй цель игрока, затрагиваемые файлы или слои, границы задачи и наблюдаемый результат. Для делегирования передай эти четыре пункта исполнителю вместе с командой проверки. Например, для сохранения хода результатом служат белая пешка на e4, очередь чёрных и единственный ход в записи после обновления страницы.
3. При исправлении дефекта воспроизведи его на исходной версии, затем повтори тот же сценарий после правки. Сохраняй согласованные критерии приёмки. Если меняется требование, обнови описание функции и проверку вместе с поведением.
4. Перед завершением сопоставь diff с критерием игрока и выполни подходящие [проверки](testing.md). В запись о принятом шаге в ROADMAP.md включи результат и чем он подтверждён. Если шаг заблокирован, укажи воспроизводимое условие и что требуется для продолжения.

По запросу о разборе сессии приведи конкретный сбой, его причину и минимальную правку, которая предотвратила бы повтор. Для особенности SQLite предложи изменение правила данных, для ошибки процесса — этого документа. Для каждого предложения покажи прежнюю и предлагаемую формулировки.
