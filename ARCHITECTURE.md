# Архитектура chessBoard

Клиент, FastAPI и SQLite обслуживают локальную партию. Файлы backend/api.py, service.py, domain.py и db.py отвечают за транспорт, игровую операцию, шахматную позицию и хранение соответственно. Миграции применяются при старте. После фиксации хода или занятия места сервер будит подписчиков этой партии. Канал WebSocket отправляет персональный снимок при подписке и последующих изменениях. Часы запланированы на следующий этап. Очередность функций и примеры приёмки приведены в [плане разработки](ROADMAP.md).

Основная поставка — веб-приложение. Клиент работает с браузерными URL и относительными адресами API. Дебютные линии исполняются в клиенте, а тактические позиции загружаются из отдельного SQLite-каталога через HTTP. Возможная упаковка для десктопа рассматривается после стабилизации веб-сценариев.

## Клиент

Точка входа монтирует React. Слой `app` собирает приложение, `pages/game` выбирает позицию для экрана, `entities/board` рисует переданные фигуры. Стартовая позиция, типы координат и визуальные ресурсы лежат рядом с доской. Каждый внешний потребитель получает компоненты и типы через `index.ts` соответствующего модуля. Локальные CSS-модули изолируют стили клеток и фигур.

При добавлении игры выделить в `features/play` выбор клетки, превращение и отправку хода. Выбранная клетка принадлежит текущему экземпляру доски. Серверный снимок принадлежит экрану партии. Так в разборе можно открыть две позиции одновременно. Общий клиент HTTP и обработку переподключения выделить при первом сетевом сценарии. В запросах, событиях и моделях интерфейса использовать одно обозначение полей, например `e2`.

Зависимости направлены от app к pages, widgets, features, entities и shared. Слой добавляется вместе с первым потребителем. Внутри модуля разрешены относительные импорты. Между модулями импортировать публичную точку входа. Проверка этих границ для локальных импортов входит в `npm test`.

## Сервер партии

| Граница | Ответственность | Пример для команды хода |
|---|---|---|
| API | Проверка схемы запроса, сессии, преобразование ответа, HTTP и WebSocket | Распознать игрока и разобрать UCI, идентификатор команды и ожидаемую версию. |
| Прикладной сервис | Порядок выполнения сценария, права участника, транзакция | Узнать исход повторной команды, проверить место игрока, вызвать домен, сохранить результат. |
| Домен | Шахматные правила и переход состояния с явными входами | Получить позицию, историю и время команды, вернуть новый ход, часы и исход. Тестируется без сети и базы. |
| Репозиторий | Запросы SQLAlchemy, преобразование записей в доменные данные | Атомарно изменить партию нужной версии и записать полуход. Возвращать типизированные данные. |
| Точка сборки | Конфигурация FastAPI, подключение SQLite, создание зависимостей | Передать сервису репозиторий и источник времени. В тесте заменить часы управляемым значением. |

Один процесс и одна база покрывают игру по приглашению. Для асинхронного транспорта исключить блокирующие запросы на пути рассылки событий. Сессию БД открывать на операцию, освобождать до сетевой рассылки. Длительный анализ движком позднее выполнять вне цикла обработки ходов.

## Контракты, данные и сбои

- Описывать HTTP-команды схемами FastAPI и публиковать их в OpenAPI. Для событий WebSocket определить схему снимка и его версию. Клиент сопоставляет стабильные коды исходов с текстом интерфейса. Например, при `stale_version` он получает свежую позицию и предлагает повторно выбрать ход.
- Владельцем транзакции служит прикладной сценарий. Репозитории одной команды используют общее соединение. Конфликт версии откатывает ход, часы и журнал команды вместе. Публикация снимка происходит после фиксации. Если связь оборвалась после фиксации, повтор с прежним идентификатором возвращает сохранённый исход.
- Модели SQLAlchemy и версионные миграции Alembic хранить в backend. Уникальность номера полухода и идентификатора команды закрепить в SQLite. Использовать связанные параметры, внешние ключи на каждом соединении и короткие транзакции. Список партий читать страницами. Индексы добавлять по фактическим запросам.
- Настройки пути базы, разрешённого origin и параметров сессии читать один раз в точке запуска. Значения для разработки описать рядом с командой запуска backend, когда он появится. Файлы базы, ключи сессий и локальные настройки хранить вне Git.
- Проверять назначенную сторону для каждой команды, включая сдачу. Для браузерной сессии использовать HttpOnly cookie, HTTPS в опубликованной среде и проверку origin при изменяющих запросах и подключении WebSocket. В журнале фиксировать идентификатор партии, версию, код результата и длительность. Ключи приглашений и значения cookie в журнал не включать.

## Проверки при разработке

Сейчас `npm run build` проверяет типы и собирает клиент. `npm test` проверяет границы импортов и вывод экрана через обычный компонент приложения, включая координаты всех 32 фигур.

С первым игровым сценарием добавить три проверки. Доменный тест проигрывает ход с заданным временем. Интеграционный тест открывает временный файл SQLite и отправляет конкурирующие команды из разных соединений. Сквозной тест открывает две браузерные сессии, делает ход, переподключает соперника и сравнивает снимки. Для изменения схемы проверять миграцию существующей партии и чтение её истории после обновления.

## Связь с tuareg

Ориентиры в исходном проекте находятся в `_docs/ai/`. Правила слоёв взяты из `architecture.md` и `ui-architecture.md`, работа с состоянием и стилями — из `ui-state.md` и `ui-styling.md`. Границы транзакций, внедрение зависимостей и миграции опираются на `data-access.md`, `dependency-injection.md` и `database.md`. Для контрактов, диагностики и проверок применены подходы из `api-design.md`, `error-handling.md`, `configuration.md`, `logging.md`, `security.md` и `testing.md`.

SQLite заменяет сервер PostgreSQL в начальной архитектуре. Потребность в общем хранилище состояния React появится, когда одни данные понадобятся нескольким экранам. Очередь задач имеет смысл рассматривать при появлении длительного анализа партий. Эти решения можно принимать независимо от реализации живой доски.
